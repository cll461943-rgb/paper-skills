# paper-idea：交叉选题、反方质询与 MVP 设计

本技能负责把文献调研产出的瓶颈与技术原语转化为经得起推敲的研究提案，对应阶段门 G2（创新点）。核心做法是通过“瓶颈 × 方法”交叉矩阵定位真实空白，对候选点打分筛选，再经过严格的反方质询与最小可证伪实验（MVP）设计，由作者选定试跑方案并在 G2 完成探路执行与过门判定。

## 何时使用 / 不适用

适用情形如下。

- 已完成 `paper-scout` 的论文矩阵、核心精读卡片与瓶颈清单，准备凝练论文核心创新点。
- 手头有多个零散想法，难以判断哪个既够顶刊/顶会分量又在当前算力与时间预算内可落地。
- 原定方案在实验或审稿中被部分推翻，需要重新评估备选路线或切换论文定位（如从方法型转向分析/协议型）。

不适用情形如下。

- 文献底数尚未摸清、连主要基线和近期预印本都没查（应先回 `paper-scout`）。
- 方向已锁定并通过探路验真，进入大规模正式实验与统计分析阶段（应交由 `paper-evidence`）。
- 希望 AI 直接跳过作者确认单方面定题（违反“作者是作者”原则）。

## 输入

1. `paper-scout` 产出的 `paper_matrix.csv`、核心精读卡片与 `bottlenecks.md`。
2. 研究约束条件：可用算力上限（GPU 小时或 API 预算）、时间窗口、可接触的真实系统或基准。
3. 目标投稿去向与预期论文类型倾向（方法型、基准型或分析/发现型，可暂留多选）。
4. `paper-evidence` 提供的真实信号与无泄漏规范，用于约束 G2 的 MVP 设计与探路试跑。

## 流程

按以下七个步骤执行，每一步都有可核查的中间产物。

### 步骤 1：抽取方法原语轴，构建“瓶颈 × 方法”交叉矩阵

从精读卡片中抽离可复用的技术机制原语作为矩阵列（如 M1、M2……），将 `bottlenecks.md` 中有文献证据支撑的核心瓶颈作为矩阵行（如 B1、B2……）。逐格核对现有文献覆盖度并做三档标记：`[已占]` 表示已有完整实现并列出代表作，`[部分]` 表示仅在 Oracle 条件或局部场景触及，空白高价值格标记为候选交叉点。合并强耦合的相邻交叉格，避免把一个完整机制拆成零碎微创新。对于目前只有一篇一手证据支撑的瓶颈，单独标注证据强弱及待验证项，避免与多篇交叉印证的成熟瓶颈混为一谈。

可检查产出：`bottleneck_method_matrix.md`（含原语说明表、完整交叉矩阵、证据强弱标注与空白簇列表）。

### 步骤 2：建立创新点池并触发专项查新

将交叉矩阵中筛出的 4 至 6 个候选簇写成标准候选条目，写明各自解决的瓶颈、核心原语组合、预期论文类型与资源门槛。立刻将每个候选送回 `paper-scout` 执行专项查新（必须含最近 3 个月预印本核查），过滤掉红灯撞车项，并将黄灯项的重叠边界写进候选说明。每份查新报告都要列出最接近的工作、关键差异、检索截止日期与缺失索引，结论严格限定在检索覆盖之内，表述为“在已检索范围内未发现同机制工作”。若后续改题、切换备选路线或久拖未投，必须在继续推进前触发增量复查。

可检查产出：`idea_pool.md`（创新点池）及对应的专项查新报告链接。

### 步骤 3：多维打分与粗筛

参照 [references/idea_scoring.md](references/idea_scoring.md) 中的六个维度，对通过查新的候选逐项打分并给出评分依据，包括问题真实性、查新稀缺度、机制不可替代性、证据闭环可行性、MVP 速度与资源成本、去向匹配度。禁止只凭“方法听起来高级”排序，把高算力方向与轻量方向分别标出前置预实验门槛，筛出 2 至 3 个进入下一轮质询。

可检查产出：带理由与约束标注的评分表（写入 `idea_pool.md`）。

### 步骤 4：反方质询（模拟苛刻审稿人）

对入围的每个候选独立执行反方质询，至少书面回答以下七个尖锐问题。

1. 如果审稿人用一句话刻薄地概括本方法，会怎么说（例如“不过是规则加 LLM 再加启发式过滤”）？你如何证明它不止于此？
2. 你用来证明问题存在的数据源，和用来评测方法的数据源，是不是同一个真实闭环？会不会出现前半篇讲问题 A、后半篇解问题 B 的错位？
3. 去掉方案里最花哨的组件，只留强基线加最简版本，核心指标还会明显领先吗？
4. 若把合成观测或真值辅助信号全部拔掉，完全改用真实通道，核心机制还能站得住吗？
5. 如果核心假设被实验证伪，这个方向有没有退路（比如转成高价值的实证发现或评测协议论文）？
6. 本方案的算力、API 费用或人工标注成本是否在团队承受范围内？有没有低成本探路实验？
7. 哪个近似工作最容易拿来拒稿，你需要把哪篇论文设为必测强基线？

可检查产出：每个入围候选的 `devils_advocate_<id>.md`（反方质询与回应记录）。

### 步骤 5：设计最小可证伪实验（MVP）

在正式投入数周开发前，为首选与次选分别设计 3 至 7 天内可跑完的 MVP。MVP 必须满足三个条件：直击最脆弱的核心假设，使用真实或最小闭环数据而非纯理想仿真，预先写明量化通过线与止损撤退线。实验方案须接入 `paper-evidence` 提供的无泄漏与真实信号规范，避免在探路阶段偷看评测数据或混入派生信号。对于算力门槛高的备选方案，设计低成本预实验（例如先在小样本上做成本重计价或诊断探针）来决定是否启动。

可检查产出：每个入围候选的 MVP 实验单（含目标假设、最小数据、无泄漏约束、基线对照、预期成本、通过与止损判据）。

### 步骤 6：形成“三选一”决策提案并由作者选定试跑方案

汇总交叉矩阵位置、检索覆盖内的查新结论、评分、反方质询软肋与 MVP 方案，按 [references/idea_scoring.md](references/idea_scoring.md) 里的提案模板整理成一页纸的“三选一”提案（如 1 条主线加 2 条差异化备选，明确各自适用条件与风险）。交给作者或导师讨论拍板，由作者选定进入探路执行的试跑方案，记录选择依据及放弃或暂存其他候选的原因，不替作者做决定。

可检查产出：`proposal_top3.md` 与作者签字确认的试跑方案选择记录。

### 步骤 7：执行 MVP 探路并产出过门结论

作者选定试跑方案后，在 G2 阶段直接启动探路执行。执行过程严格遵守 `paper-evidence` 提供的无泄漏规范与真实信号要求，不得跳过试跑空谈结论。由 `paper-idea` 汇总并记录探路实际结果、所用代码与数据版本、对照预设通过线的核验结论以及放行或止损决定。

过门分流按三种结果处理。探路达到预设通过线时，产出完整 MVP 结论并进入 G3 正式实验。探路证伪核心假设或触发止损线时，记录失败原因并退回候选池，改选备选方案或调整论文定位。若当前算力、数据许可或时间预算不足而无法立即试跑，必须显式标记为“待验证”，写明缺失条件、补跑节点与风险边界，严禁将未跑方案记为已验证通过。

可检查产出：`mvp_report_<id>.md`（含实际运行结果、代码与数据版本、通过线核对与止损决定；预算不足时记录“待验证”状态及补跑条件）。

## 检查清单

- [ ] 交叉矩阵的每个 `[已占]` 或 `[部分]` 格子都附有具体代表作，没有凭印象标空；单篇一手证据的瓶颈已标注证据强弱及待验证项。
- [ ] 每个入围候选都通过了含近 3 个月预印本扫描的专项查新，报告写明最接近工作、关键差异、检索截止日与缺失索引，结论限定在已检索范围内。
- [ ] 评分表包含证据闭环与算力成本维度，没有只按纸面新颖度排序。
- [ ] 每个候选都完成了反方质询书面记录，正视了“一句话概括”与“问题-方法错位”风险。
- [ ] 首选方案已设计最小可证伪实验（MVP），接入 `paper-evidence` 无泄漏规范，并写清提前止损的量化条件。
- [ ] 作者已明确选定试跑方案并留档备选切换条件，未由 AI 代做定题决策。
- [ ] 已完成 G2 探路执行，记录实际结果、版本、通过线核对与止损决定（预算不足则标为“待验证”并列明补跑条件），并按分流规则决定进入 G3 或退回候选池。

## 常见失败

1. 凭纸面“方法排序”直接锁定方案，跳过反方质询与 MVP 探路。某真实研究项目曾按纸面设计直接锁定主方案并投入数周实验，结果在后期复核时三条核心主张被推翻两条，原本主打的贝叶斯回合归因在真实观测通道下失效。规避办法是把反方质询和最小可证伪实验前置到立项之前，先在 G2 用最小成本试跑最脆弱的环节。
2. 问题来源与主方法输入错位，两条证据链永不相交。在 LLM agent 记忆审计项目中，真实系统（mem0）里观察到的故障是没有失效日志的写入问题，但主方法却建立在存在失效日志的受控基准上，导致前半篇证明问题 A、后半篇解决方法 B，被三方审稿人一致拒稿。规避办法是在反方质询中强制核对“真实现象与主方法是否在同一系统上闭环”。
3. 核心机制过于单薄，被审稿人一句话打成工程拼接或贴标签。部分方案看似包含多个模块，去掉规则或强提示词后却讲不清独立机理；另有方案为了贴合某本期刊事后硬加理论标签，正文并无对应支撑。规避办法是在质询环节预先写出最刻薄的一句话概括，若无法用机制和消融反驳，就重做设计或改定为分析/发现型论文。
4. 忽略算力与工程约束，把高门槛方向当作默认主线。未评估 GPU 小时或标注预算就直接开干，做到一半资源耗尽被迫拼装交稿。规避办法是在打分和提案阶段明确标注资源门槛，高成本路线必须先跑低成本预实验，预算不足时如实标为“待验证”而非强行过门。

## 与其他技能的衔接

- 上游来源：接收 `paper-scout` 的论文矩阵、精读卡片与瓶颈清单。
- 横向协同：候选生成后调用 `paper-scout` 的专项查新流程（改题或久拖未投时触发增量复查）；MVP 设计与探路执行前接入 `paper-evidence` 提供的真实信号与无泄漏规范。
- 下游去向：作者在 `proposal_top3.md` 中选定试跑方案，完成 G2 探路执行并产出 `mvp_report_<id>.md`（达到通过线，或经作者确认的“待验证”及补跑约束）通过 G2 后，将选定方案、核心假设和 MVP 结论移交给 `paper-evidence` 制定完整实验协议。
