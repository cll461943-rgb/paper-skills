# 交付门与验收清单（delivery_gate.md）

任何交给人（研究者、导师、合作者或审稿人）看的论文相关文档，在宣布“可以交付”前，必须完整走完以下五关。缺少任何一关，只能以“内部工作草稿”名义流转，不得声称验收通过。

---

## 第一关：主控模型通读全文

数字核对脚本不能替代阅读。主控模型必须把交付稿从头到尾连续读完，禁止只抽读前几十行或只搜索关键词。

- [ ] 连续读完摘要、引言、相关工作、方法、实验、讨论、结论及图表说明。
- [ ] 检查跨章节重复：同一组数字或结论是否在多章反复堆砌（摘要只保留 2 至 3 个核心数字）。
- [ ] 检查叙事连贯：问题动机、研究问题（RQ）、贡献条目与实验章节是否一一对应。
- [ ] 检查拼装痕迹：各章人称、时态、术语、符号、引用清单风格是否统一。
- [ ] 检查内部代号：确认无实验轮次号、脚本名、旧版本名、源码路径或 commit 号混入正文。
- [ ] 检查未完成项：所有待补内容是否集中列在单处清单，正文中没有散落红字标注。

## 第二关：事实、数字与图表核对（底线检查）

这一关是底线，不代表质量达标。

- [ ] 正文、表格与图中的每一个数值均能追溯到最终实验产物，三处数值完全一致。
- [ ] 主表只加粗最终方法，未误加粗已弃用版本。
- [ ] 所有数据图均基于最终方法绘制，无旧图残留。
- [ ] 图 1 为具体实例 teaser；方法图只画已实现路径；无跨组误导连线或双轴歧义；全套图色义与字号统一。
- [ ] 题目、摘要与贡献条目中没有超出当前实验证据的声称。

## 第三关：至少两家不同模型独立盲审与元审稿

交付完整初稿、重大改稿或返修包前，必须组织独立审稿：

- [ ] 至少 2 家与主起草方不同（或彼此不同）的模型家族独立完成只读审稿，输出各自 `review_*.md`。
- [ ] 审稿人之间相互隔离，禁止把第一家审稿意见喂给第二家以防跟风。
- [ ] 汇总产出 `meta_review.md`，明确列出多方共识问题与分歧点。
- [ ] 每条意见均已区分“表述问题”与“方法缺陷”，并给出“可救性”判断。

## 第四关：致命问题清零或正式降格/回退

对元审稿识别出的每一条致命问题，逐一闭环，不得带病交付：

- [ ] 可靠改写解决的表述问题：已完成修改并复读确认。
- [ ] 缺乏证据的过度声称：已从题目、摘要和贡献中撤下，降格为局限或未来工作。
- [ ] 涉及真信号失效、构造同构、数据源错位或方法分量不足的硬伤：已通知 `paper-pilot` 回退至 G3/G4/G5 补齐，或整理定位选项交作者拍板，未强行交付。

## 第五关：随稿附上诚实的交付说明

每次交付时，必须在回复或文档顶部附上以下交付说明，如实披露核查范围，绝不夸大把关程度：

```markdown
### 交付说明
- 交付物与版本：`<文件名与版本号>`
- 完整通读范围：`列出主控模型从头到尾完整读过的章节或文件`
- 未读或仅抽查范围：`如实写出；正式交付稿此处应为“无”`
- 参与独立审稿的模型：`模型 A（结论摘要）、模型 B（结论摘要）`
- 致命问题处置：`列出共识致命问题编号及清零/降格状态`
- 待作者拍板或集中待补项：`列出需作者决定的方向分叉，及 status.md 中未关闭项编号`
```

## 不予放行红线

出现以下任意一条，立即拦截交付，退回返工或回退上游阶段门：

1. 主控模型未通读全文。
2. 独立审稿模型不足 2 家，或存在“写手自审”。
3. 仍有未处理的共识致命问题（例如题目承诺的能力完全没有实验支撑）。
4. 正文散落未归口的红字占位或内部工程代号。
